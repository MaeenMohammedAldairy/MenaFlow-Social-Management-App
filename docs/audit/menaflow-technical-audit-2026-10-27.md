# التدقيق التقني الشامل لمشروع MenaFlow

**تاريخ الفحص:** 27 أكتوبر 2026  
**النطاق:** المستودع كما كان في مساحة العمل الحالية، بما يشمل الملفات المتتبعة والتغييرات المحلية الظاهرة.  
**الفرع:** `main`  
**القرار:** لا أوصي باعتبار هذه النسخة جاهزة لإطلاق إنتاجي قبل معالجة أولويات الأداء والحماية والتحقق من بيئة التشغيل أدناه.

## 1. الملخص التنفيذي

المشروع تطبيق متعدد الحزم يضم واجهة Expo Router، وخادم Express، وعقود OpenAPI مولّدة، ومخططات Drizzle، وترحيلات Supabase، وتكاملات Meta وEvolution وموفري الذكاء الاصطناعي. توجد ضوابط إيجابية ملموسة: المصادقة عبر Clerk، وحل مركزي لسياق مساحة العمل، وتحقق توقيع Meta والتحقق من سر Evolution، وتشفير رموز Meta، واستخدام مفاتيح فريدة وفهارس للبيانات الأساسية، واختبارات وحدات تغطي أجزاء مهمة من منطق التكاملات.

مع ذلك، لا تتوافر أدلة كافية لإقرار جاهزية الإنتاج: قياسات المتصفح المحلي أظهرت طلبات API بلغت نحو 7 إلى 19 ثانية؛ واجهة الويب لا تعرّف اتجاه المستند RTL رغم المحتوى العربي؛ لم يُعثر على تحديد معدل للطلبات داخل التطبيق؛ ولم تُتحقق بيئة قاعدة البيانات الإنتاجية أو خطط الاستعلام أو النسخ الاحتياطية أو سلوك النشر. كما أن مساحة العمل غير نظيفة على نحو يمنع التعامل مع الحالة الحالية كإصدار ثابت.

**التقييم المختصر**

| المحور | النتيجة |
|---|---|
| بنية المنتج | حدود الحزم واضحة إجمالاً، لكن عدة ملفات عالية المسؤولية والحجم |
| صحة الأنواع والاختبارات | `pnpm run typecheck` نجح؛ 200 اختبار وحدة نجح عبر كل ملفات الاختبار المكتشفة |
| أداء الواجهة | قياس محلي واحد/جلسة مشتركة؛ توجد ذيول بطيئة جداً في طلبات API والوسائط |
| UI/UX والعربية | عناصر عربية وتوجد تسميات وصول كثيرة؛ اتجاه مستند الويب المقاس `ltr` |
| عزل المساحات | حارس مركزي ومرشحات مساحة عمل ظاهرة في المسارات، لكن لم يُختبر عزل حي أو RLS على قاعدة فعلية |
| الأمان | التحقق من Webhooks وتشفير الرموز موجودان؛ لم يُعثر على rate limiting بالتطبيق |
| جاهزية التشغيل | لم تُثبت مراقبة وتنبيهات ونسخ احتياطية أو نشر/استعادة فعليان |

## 2. منهجية الفحص وحدوده

- جُردت ملفات المستودع ثم روجعت إعدادات الحزم، ومسارات Expo Router، ونقاط تشغيل الخادم، ومخططات/ترحيلات DB، والاختبارات والوثائق ذات الصلة؛ وتتبعت مسارات البيانات والتكاملات عبر بحث موجّه وقراءة الملفات المحورية، لا قراءة حرفية لكل ملف.
- استُخدمت صفحة التطبيق المحلية المشتركة لالتقاط قياسات Navigation/Resource Timing وقراءة اتجاه النص؛ لم تُجرَ اختبارات ضغط أو تغييرات على واجهة المستخدم أو قاعدة البيانات.
- شُغّلت الاختبارات واختبارات TypeScript فقط. لم تُشغّل الترحيلات، ولم تُستعلم قاعدة بيانات، ولم تُجرّب اتصالات فعلية بـMeta أو Evolution أو AI.
- لم يُقرأ محتوى ملفات الأسرار ولم تُدرج أي رموز أو بيانات حسابات أو عملاء في التقرير.
- **حالة مساحة العمل مهمة:** أظهر `git status` عدد 192 إدخالاً محلياً (73 تغييراً/حذفاً لملفات متتبعة و119 ملفاً غير متتبع). لذلك النتائج تخص شجرة العمل الحالية ولا تمثل مقارنة نظيفة مع commit معلوم. لم أعدّل أو أحذف أيّاً من هذه التغييرات.
- متصفح التطوير مشترك ويمكن أن تتغير صفحته أثناء القياس؛ القياسات الواردة أدناه مشاهدات فعلية للجلسة وليست تجربة مخبرية قابلة للمقارنة أو قياساً للإنتاج.

## 3. خريطة البنية وتدفق البيانات

```text
Expo Router / React Native (iOS + Android + Web)
       │
       ├── api-client-react (عميل React Query مولّد)
       │       └── api-zod / OpenAPI
       ▼
Express API + Clerk
       ├── workspace-context / owner-access
       ├── Drizzle → PostgreSQL على Supabase
       ├── Supabase Storage للوسائط
       ├── Evolution API ↔ WhatsApp (اتصال ومزامنة وWebhook)
       ├── Meta OAuth / Graph API / Webhooks / Inbox
       └── OpenAI أو Gemini → اقتراحات/ردود الذكاء الاصطناعي
```

- نقطة تشغيل الخادم هي [index.ts](../../artifacts/api-server/src/index.ts)، والتطبيق والوسائط العامة وترتيب المصادقة وCORS في [app.ts](../../artifacts/api-server/src/app.ts).
- الواجهة مبنية على Expo Router؛ نقطة الغلاف في [_layout.tsx](../../artifacts/menaflow-mobile/app/_layout.tsx)، وتظهر مسارات المحتوى والمصادر والوارد والتقارير والإعدادات ضمن `app/(tabs)`.
- اتجاه الاعتماد المقصود جيد إجمالاً: الواجهة → عميل API → مخططات API؛ الخادم → مخططات API وقاعدة البيانات. حزمة `mockup-sandbox` تطبيق Vite منفصل ومعلن عنه كـmockup، وليست واجهة Expo.
- المصادقة تتحول إلى `userId` من Clerk ثم إلى عضوية مساحة عمل عبر [workspace-context.ts](../../artifacts/api-server/src/lib/workspace-context.ts) و[workspace-resolution.ts](../../artifacts/api-server/src/lib/workspace-resolution.ts). معظم مسارات البيانات تعتمد `requireWorkspace` وتستخدم `workspaceId` في المرشحات.
- الترحيلات في `supabase/migrations` تشمل جداول العمل والمحتوى وWhatsApp وMeta. لا يمكن تأكيد أن هذه الترحيلات مطبقة على أي بيئة أو مطابقة للمخطط الحي دون اتصال مصرح وآمن بها.

## 4. الأداء والاستجابة

### قياسات فعلية من جلسة المتصفح المحلية

عند التقاط أول قراءة كانت الصفحة `/content` على منفذ التطوير وبمساحة عرض 940×717:

| المقياس | المشاهدة |
|---|---:|
| `responseStart` للتنقل | 242 ms |
| `DOMContentLoaded` | 1,751 ms |
| `loadEventEnd` | 1,768 ms |
| حزمة Metro التطويرية `entry.bundle` | 2,046,881 بايت |

في قراءة لاحقة، بعد أن تراكمت موارد الجلسة المشتركة وتغير المسار داخل التطبيق، احتوى سجل Resource Timing على **115 مورداً و55 طلب API**:

| المقياس على موارد API المسجلة | المشاهدة |
|---|---:|
| P50 | 691 ms |
| P95 | 6,994 ms |
| P99 / الحد الأعلى المرصود | 19,077 ms |
| `/api/social/connections` | 4 مرات؛ الحد الأعلى 19,077 ms |
| `/api/auth/access` | 3 مرات؛ الحد الأعلى 15,092 ms |
| `/api/posts/page` | 4 مرات؛ الحد الأعلى 6,994 ms |
| `/api/social/whatsapp/public-media/:id` | 40 طلباً؛ حد أعلى مرصود 4,673 ms |

هذه الأرقام **قياس محلي حقيقي لكنه غير مضبوط**: سجلّ الموارد متراكم خلال جلسة مشتركة وليس عينة طلبات مستقلة تحت ظروف ثابتة؛ P99 هنا يقع عملياً عند أقصى مشاهدة. زمن الحزمة يخص Metro في التطوير وليس حجم حزمة إنتاج. لا توجد عينة من بيئة الإنتاج أو إحصاءات خادم أو حالة HTTP/خطة تنفيذ DB تتيح عزو زمن البطء إلى سبب واحد.

### نقاط الاختناق المحتملة/المرصودة

1. **التحقق من حالة اتصال WhatsApp ضمن مسار استجابة الاتصالات:** `/social/connections` ينفذ قراءتي DB متتاليتين ثم ينتظر `evolutionConnectionState` عندما توجد وصلة WhatsApp؛ الطلب الخارجي له مهلة 15 ثانية. الترتيب موجود في [social.ts](../../artifacts/api-server/src/routes/social.ts#L77) و[evolution.ts](../../artifacts/api-server/src/lib/whatsapp-evolution.ts#L127). قياس 19.1 ثانية حقيقي، لكن مساهمة كل مرحلة غير مقاسة؛ لا يثبت وحده أن Evolution سبب كامل التأخير.
2. **سياق مساحة العمل على الطلبات الأولية:** `/auth/access` يمر عبر `requireWorkspace`، الذي يحل العضوية داخل معاملة وقد ينشئ مساحة أولى عند عدم وجود عضوية. ظهر حد أعلى 15.1 ثانية لطلب هذا المسار في الجلسة. السبب قد يكون انتظار DB أو مزود قاعدة البيانات أو التهيئة، لكنه غير محسوم دون مقاييس اتصال واستعلام حي.
3. **تحميل الوسائط:** سجل الجلسة تضمن 40 طلب وسائط عامة، وأقصى زمن مرصود 4.67 ثانية. المسار يوقّع رابط الوسيط ويقرأه/يبثه من التخزين عبر [whatsapp-messages.ts](../../artifacts/api-server/src/routes/whatsapp-messages.ts#L876) و[whatsapp-media-storage.ts](../../artifacts/api-server/src/lib/whatsapp-media-storage.ts). صفحة المحتوى تعرض صور المنشورات وتستخدم التمرير في [ContentPostList.tsx](../../artifacts/menaflow-mobile/components/content/ContentPostList.tsx#L140). لا يمكن الجزم من السجل وحده إن كل الطلبات تخص تحميلًا أولياً أو إعادة عرض/إعادة محاولة.
4. **البيانات المعروضة:** `/posts/page` يحدد الصفحة بحد أقصى 50 صفاً، وهذا يحد حجم الاستجابة النصية، لكن التحميل المتعدد للصور يظل مكلفاً على شبكة بطيئة. لا توجد قياسات ذاكرة أو أداء على هاتف ضعيف.
5. **إدارة React Query:** يُنشأ `QueryClient` بإعدادات افتراضية عامة، بينما تُضبط مدة stale لاستعلامي الاتصالات والإعداد الأولي فقط في [_layout.tsx](../../artifacts/menaflow-mobile/app/_layout.tsx#L35). وجود طلبات متكررة في سجل الجلسة لا يثبت إعادة تصيير أو retry بعينه؛ يلزم تتبع queryKey وسبب refetch لكل طلب.

### ملفات غير مستخدمة/تبعيات

- لم يثبت وجود ملف صفحة/مسار مهجور؛ فـExpo Router يسجل صفحات المجلدات تلقائياً، كما أن الحزم والمهام المولدة قد تُستخدم عبر الإعدادات.
- `isOwnerRequest` معلّمة deprecated في [owner-access.ts](../../artifacts/api-server/src/lib/owner-access.ts)، ولم يظهر لها مستهلك إنتاجي في بحث المراجع؛ ظهرت في تعريفها واختبارها فقط. **مرشح كود ميت**، لكن تحقّق من أي استهلاك خارجي قبل الإزالة.
- عُثر على ملفي نص سياقي بعنوان `Attached Element Context from Integrated.txt` داخل `artifacts/api-server/src/lib` و`lib/api-zod/src/generated`. لا توجد مراجع مصدرية ظاهرة لهما؛ هما **مرشحا ملفات زائدة منخفضا الثقة**، وقد يكونان مرفقين محليين، لذا لم يُحذف أي منهما.
- لم يُثبت وجود اعتماد npm زائد. لا يوجد في المشروع تحليل موثوق لتغطية التبعيات؛ يلزم تشغيل analyzer في بيئة نظيفة ومراجعة الإضافات الديناميكية قبل إزالة أي اعتماد.
- `artifacts/mockup-sandbox` حزمة Vite ضمن workspace لكنها موصوفة بأنها sandbox مستقل؛ لا تعتبر غير مستخدمة دون قرار منتج صريح.

## 6. UI/UX وإمكانية الوصول

### ملاحظات مثبتة

- شاشة المحتوى تعرض واجهة عربية وتحتوي بحثاً وتصفية حسب الحالة والمنصة والتاريخ، وتحمي عمليات التحرير/النشر برسائل خطأ في الكود؛ المكونات تعرض حالة التحميل والفراغ في عدة تدفقات.
- توجد تسميات `accessibilityLabel` وأدوار للأزرار في المكونات، خصوصاً المحتوى والمصادر. هذه نقطة إيجابية لكنها لا تعوّض اختبار قارئ شاشة كامل.
- على الويب، كانت `document.documentElement.dir` غير مضبوطة و`getComputedStyle(document.body).direction` تساوي `ltr` في الصفحة المقاسة. الكود يفرض RTL فقط عندما `Platform.OS !== "web"` في [_layout.tsx](../../artifacts/menaflow-mobile/app/_layout.tsx#L135). هذا دليل على نقص اتجاه المستند الدلالي للويب؛ قد يؤثر على ترتيب المؤشرات والنص المختلط والتنقل بقارئ الشاشة. لا يثبت ذلك أن كل عنصر مرئي معكوس، فبعض العناصر تستخدم تنسيقاً محلياً.
- تدفق المحتوى قد يعرض عدداً كبيراً من معاينات الصور؛ قياس الجلسة رصد 40 طلب وسيط. افحص التحميل الكسول وأحجام الصور المصغرة وعدم تحميل الوسائط خارج الشاشة.
- لم تُختبر واجهات iOS/Android على جهاز أو محاكي، ولم تُختبر أحجام الهاتف/اللوحي/تكبير الخط أو قارئ الشاشة. نافذة المتصفح المقاسة كانت 940×717 فقط.
- لم يُجر اختبار يدوي لتدفقات تسجيل الدخول/التهيئة/ربط Meta وWhatsApp/الردود/النشر؛ نجاح اختبارات المنطق لا يثبت اكتمال الحالات الفعلية أو التعامل مع انتهاء جلسة Clerk أو انقطاع الشبكة.

### اقتراحات UI عملية

1. تعريف `dir="rtl"` و`lang="ar"` على جذر الويب، مع اختبار المحتوى المختلط والأرقام والبريد وعناوين URL.
2. اختبار الشاشات الرئيسية بعروض 320/360/390/768/1024 بكسل، ومع تكبير الخط ولوحة مفاتيح مفتوحة.
3. تحقق من حالات التحميل والفراغ والخطأ وإعادة المحاولة لكل شاشة، خاصة المصادر والوارد والمحتوى والنشر.
4. استخدام صور مصغرة متجاوبة وتحميل كسول/افتراضي مع قياس عدد طلبات الوسائط والبايتات خلال فتح صفحة المحتوى.
5. اختبار قارئ شاشة لـVoiceOver وTalkBack، وتسلسل التركيز، وتسميات الحقول ورسائل التحقق، وعدم الاعتماد على اللون وحده للحالة.

## 7. الخادم وقاعدة البيانات والتكاملات

### ما يبدو سليماً من الكود

- المسارات الاعتيادية تستعمل `requireWorkspace`، ومسار Meta webhook يتحقق من HMAC على الجسم الخام، وWebhook Evolution يتحقق من `x-evolution-api-key` قبل المعالجة. راجع [meta-webhook.ts](../../artifacts/api-server/src/routes/meta-webhook.ts) و[whatsapp-sync.ts](../../artifacts/api-server/src/routes/whatsapp-sync.ts#L513).
- الترحيلات تمكّن RLS وتلغي صلاحيات `anon` و`authenticated` للجداول الأساسية في [20261019001000_lock_down_app_tables.sql](../../supabase/migrations/20261019001000_lock_down_app_tables.sql). كما توجد قيود فريدة وفهارس على مفاتيح workspace والرسائل والطوابير في الترحيل الأول.
- توجد آليات منع ازدواج/تزامن في أجزاء من المعالجة: `onConflictDoNothing` عند إدخال أحداث Meta، و`SKIP LOCKED` في بعض عمّال الطوابير، واختبارات لمنطق retry ونطاقات مساحة العمل.
- أكثر اتصالات HTTP المهمة التي فُحصت تضبط مهلاً صريحة؛ أمثلة 15 ثانية لـEvolution/Meta، و30 ثانية للـAI افتراضياً، و60–120 ثانية لتخزين الوسائط. لكن طول هذه المهل قد ينعكس مباشرة على زمن الطلب المتزامن، ولا يوجد قياس تشغيلي يوضح معدل انتهاء المهلة.

### مخاطر/نواقص تشغيلية

1. **تحديد معدل الطلبات:** لم يظهر middleware أو اعتماد `express-rate-limit` في التطبيق/حزمة الخادم. قد توجد حماية لدى بوابة الاستضافة لم يمكن فحصها؛ لذلك لا أعد غيابها مثبتاً على مستوى البنية كلها. يلزم تحديد حدود خاصة لمسارات AI وOAuth وعمليات الربط والويب هوك، مع حدود متوافقة مع سياسة Meta.
2. **حدود اتصال قاعدة البيانات:** إنشاء `pg.Pool` في [index.ts الخاص بقاعدة البيانات](../../lib/db/src/index.ts#L37) يمرر عنوان الاتصال فقط ولا يصرح `max` أو مهلة اتصال أو سلوك انتظار. إعدادات المكتبة الافتراضية قد لا تكون ملائمة عند زيادة نسخ الخدمة؛ احسب الحد الإجمالي للاتصالات بحسب عدد النسخ، واضبطه بعد مراجعة الحد الفعلي لدى Supabase.
3. **العمّال داخل خادم API:** يبدأ الخادم دوريات تنزيل وسائط وصور مصغرة وردود Meta في كل عملية API عند عدم تعطيل متغيراتها في [index.ts](../../artifacts/api-server/src/index.ts#L31). هذا يضاعف حمل polling مع كل نسخة. بعض الطوابير تستخدم قفل صف، لكن لم يُثبت أن كل طابور يملك claim/lease ومهلة استرداد صحيحة أو أن معدل التشغيل مضبوط مركزياً.
4. **RLS وعزل workspace:** الترحيلات تفعّل RLS ولا تنشئ سياسات `CREATE POLICY` في الملفات المفحوصة؛ الوصول الممنوع افتراضياً عبر أدوار Supabase العادية جيد، لكن تطبيق الخادم يتصل مباشرة بـPostgres ويعتمد أيضاً على صلاحيات دوره ومرشحات `workspaceId`. لم يُتحقق من دور `DATABASE_URL` أو ما إذا كان يتجاوز RLS أو من العزل على قاعدة حية. يجب اعتبار اختبارات عزل كل المسارات شرط إصدار.
5. **رمز Meta في عنوان URL:** `account-details.ts` يضيف `access_token` إلى query string في طلب Graph (`graphRequest`). الاتصال HTTPS، ولم يثبت تسجيل الرمز في نظام ما، لكن عناوين URL أسهل تسرباً إلى سجلات/آثار الوسيط من ترويسة Authorization. استخدم ترويسة معتمدة من Graph حيثما أمكن، أو وثّق سبب الاستثناء وتأكد من تنقيح سجلات الخروج.
6. **حالة قاعدة البيانات:** توجد فهارس مناسبة للعديد من استعلامات مساحة العمل والرسائل، وحدود للصفحات، لكن لم تتوفر `EXPLAIN ANALYZE` أو أحجام جداول أو سجلات DB؛ لا يمكن إثبات/نفي استعلام بطيء أو N+1 من المخطط وحده.
7. **الاعتمادية والمراقبة:** توجد سجلات Pino ونقطتا `/healthz` و`/readyz`؛ readiness يفحص DB فقط ولا يقدم صحة Evolution أو Meta أو الطوابير. لم يُعثر ضمن الكود المفحوص على مقاييس زمنية/معدل أخطاء/طول طوابير أو تكامل تنبيهات. توافر هذه الأشياء في منصة الاستضافة غير متحقق.
8. **النسخ الاحتياطي والاستعادة:** لا يمكن إثبات سياسة النسخ أو اختبار استعادة من ملفات المصدر. وثّقوا RPO/RTO، واحتفظوا بنسخة خارجية، واختبروا استعادة قاعدة ووسائط قبل اعتبار الإنتاج جاهزاً.

## 10. خطة تحسين مرتبة

### عاجل قبل اعتماد الإنتاج

1. تثبيت commit نظيف ومراجعة حالة الملفات المحلية خارج هذا التدقيق.
2. إضافة قياس tracing آمن لكل مرحلة في `requireWorkspace` و`/social/connections` و`/posts/page`، ثم معالجة التأخير بناءً على القياس لا التخمين.
3. فرض تحديد معدل للـAPI المكلف والحساس، والتأكد من أن أي حماية خارجية موثقة ومختبرة.
4. التحقق على بيئة staging من دور DB وRLS وعزل كل workspace؛ لا تعتمد على RLS مفعّل اسماً فقط.
5. مراجعة إعدادات أسرار الإنتاج وClerk وMeta وEvolution وStorage دون تضمين القيم في السجلات.
6. استعادة نسخة احتياطية تجريبية وإثبات RPO/RTO قبل إطلاق بيانات عملاء.

### أداء واستقرار

1. فصل فحص حالة WhatsApp عن استجابة قائمة الاتصالات أو إعادة استخدام نتيجة حديثة قصيرة العمر.
2. تعيين حدود pool والمهلة وفق سقف اتصالات قاعدة البيانات وعدد النسخ.
3. تدقيق claim/lease وإعادة المحاولة وidempotency لكل worker، وضبط concurrency وإيقافه graceful عند إنهاء العملية.
4. تحسين تحميل الصور المصغرة والتدريجي وقياس زمن API على staging؛ لا تستخدم ضغطاً على الإنتاج.
5. إضافة مؤشرات زمن الاستجابة ومعدل الأخطاء، تأخر الطوابير، انتهاء صلاحية الرموز، وحالة provider.

### إعادة تنظيم وصيانة

1. تقسيم `sources.tsx` و`posts.ts` و`whatsapp-sync.ts` و`whatsapp-messages.ts` تدريجياً مع اختبارات قبل/بعد.
2. راجع المرشحين `isOwnerRequest` وملفي السياق النصيين مع مالك المشروع؛ لا تحذف دون تحقق من الاستخدام خارج المستودع.
3. أضف CI لتشغيل TypeScript والاختبارات وكل ملفات الاختبار وlint وbuild على checkout نظيف، ثم تقرير dependency/CVE.

### تجربة المستخدم

1. تعيين RTL دلالياً على Web واختبار صفحة الدخول/المصادر/المحتوى/الوارد/النماذج.
2. اختبارات Responsive وVoiceOver/TalkBack وتكبير الخط وتدفق لوحة المفاتيح.
3. إظهار حالة provider/المزامنة/انتهاء الجلسة ورسالة الخطأ مع إجراء قابل للتنفيذ، ثم اختبار انقطاع الشبكة واستعادتها.
