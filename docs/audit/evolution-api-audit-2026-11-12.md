# تقرير مراجعة تكامل Evolution API

**تاريخ المراجعة:** 12 نوفمبر 2026

**النطاق:** تكامل Evolution API الخاص بواتساب داخل الخادم `artifacts/api-server`، وليس تدقيقًا لمصدر Evolution API أو خادمها المنشور.

## الخلاصة التنفيذية

التكامل منظم حول عميل مشترك، ويغطي إنشاء نسخة واتساب وربطها، قراءة حالتها، إعداد الويبهوك، جلب المجموعات، مزامنة الرسائل والوسائط، والرد الآلي. توجد ضوابط جيدة لعزل مساحات العمل، والتحقق من سر الويبهوك، وإلغاء الطلب عند انقطاع العميل، والتعامل مع حالات الفشل وإعادة المحاولة.

**التقييم العام: جيد مع مخاطر تشغيلية وأمنية متوسطة قابلة للمعالجة.** لم يظهر في المراجعة عيب مؤكد يسمح لمستخدم مساحة عمل بقراءة أو حذف نسخة مساحة أخرى؛ عمليات الإدارة تبدأ من اتصال مساحة العمل وتتحقق من ملكية النسخة قبل حذفها. عولج أثناء المتابعة قبول HTTP لاتصال Evolution في الإنتاج، وأضيفت حدود لحجم استجابة API والوسائط، كما أضيف محدد معدل مستقل للويبهوك. وما زال الويبهوك قادرًا على استخدام سر API الإداري كخيار احتياطي.

تستخدم المسارات الخاصة بالتطبيق `requireWorkspace`، وتُشتق النسخة الجديدة من تجزئة معرّف مساحة العمل. تُحفظ الاتصالات والمجموعات والرسائل مع `workspaceId` و`instanceName`، وتُرفض النسخة الملتبسة عند التحقق قبل الحذف. المزامنة التاريخية لها حد افتراضي 500 ورسمي أقصى 10,000 رسالة لكل مجموعة.

## النتائج ذات الأولوية

### E1 — اتصال HTTP إلى Evolution مسموح في الإنتاج

**الحالة: عولجت. الأولوية الأصلية: متوسطة (مشروطة بإعداد HTTP).**

كان عميل Evolution يقبل `http:` أو `https:` دون قصر الإنتاج على HTTPS. عند ضبط عنوان HTTP غير محمي، كان مفتاح `apikey` يُرسل عبر اتصال غير مشفر. عُدّل التحقق في `evolutionApiConfig` لرفض HTTP عندما تكون `NODE_ENV=production`، مع استمرار السماح به في بيئات التطوير.

**التحقق:** أضيف اختبار يثبت رفض HTTP في الإنتاج وقبوله في التطوير. ينبغي أن يستخدم عنوان الإنتاج HTTPS صالحًا واتصال TLS موثوقًا.

### E2 — لا يوجد حد لحجم استجابة Evolution أو ملف الوسائط

**الحالة: عولجت. الأولوية الأصلية: متوسطة.**

كان العميل يقرأ الاستجابة كاملةً دون حد، وكان مسار تنزيل الوسائط يحول `base64` إلى `Buffer` دون حد لحجم الملف. عولج ذلك بحد افتراضي 16 MiB لاستجابات Evolution، وحد 32 MiB لاستجابة الوسائط المشفرة، وحد أقصى 20 MiB للملف بعد فك الترميز. يُتحقق من `Content-Length` ومن حجم الجسم أثناء قراءته، ومن الحجم المعلن والفعلي للوسيط قبل التخزين.

**التحقق:** أضيف اختبار يثبت رفض استجابة تتجاوز حد البايتات؛ وتُسجل تجاوزات حجم الوسائط كفشل غير قابل لإعادة المحاولة. يتوافق حد الملف مع حد وسائط المنتجات الحالي (20 MiB).

### E3 — سر الويبهوك يمكن أن يكون مفتاح Evolution الإداري

**الأولوية: متوسطة (توسيع أثر تسرب السر).**

إذا لم يُضبط `WHATSAPP_EVOLUTION_WEBHOOK_SECRET`، يستخدم الكود `WHATSAPP_EVOLUTION_API_KEY` للمصادقة على أحداث الويبهوك، كما يضع السر نفسه في إعدادات الويبهوك لدى المزود. بذلك قد يؤدي كشف بيانات إعداد الويبهوك أو سجلاته إلى كشف مفتاح API ذي صلاحية إدارة Evolution، وليس سر استقبال الأحداث فقط.

**الإجراء المقترح:** اشتراط سر ويبهوك منفصل في الإنتاج وعدم الرجوع تلقائيًا إلى مفتاح API الإداري. عند تغييره، أعد إعداد الويبهوك لدى المزود وأزل السر القديم من أي إعداد أو سجل.

### E4 — الويبهوك مستثنى من محدد الطلبات العام

**الحالة: خُفّض الخطر بإضافة محدد مستقل. تبقى المعالجة المتزامنة نقطة مراقبة تشغيلية.**

`/social/whatsapp/webhook` ما زال مستثنى من محدد API العام، لكنه أصبح يمر عبر محدد مستقل لكل IP بسقف 1,200 طلب في الدقيقة قبل تحليل الجسم. عند التجاوز يرد الخادم بـ429 مع ترويسات إعادة المحاولة. ويظل جسم الطلب محدودًا بواحد ميغابايت. المحدد يستخدم مخزن Express الافتراضي داخل الذاكرة؛ لذا يُطبّق السقف لكل نسخة من الخادم ويُعاد عند إعادة التشغيل. بعد ذلك، قد يعالج المسار الدفعات بالتتابع، وينتظر توليد رد آلي أو استدعاء المزود قبل الإقرار؛ لذلك تبقى المعالجة المتزامنة نقطة مراقبة عند الأحمال العالية.

**الإجراء المقترح:** مراقبة معدل الويبهوك وزمن المعالجة وإعادات المحاولة وضبط السقف وفق حركة الإنتاج. إذا سببت المعالجة المتزامنة تأخيرًا أو إعادة إرسال متكررة، انقل الأعمال البطيئة إلى طابور دائم قبل الإقرار بالحدث.

### E5 — الحد الأقصى لطلب استيراد السجل التاريخي مرتفع

**الحالة: عولجت. الأولوية الأصلية: متوسطة.**

كان الحد الأقصى 100,000 رسالة لكل مجموعة. خُفّض إلى 10,000 رسالة لكل مجموعة على الخادم والواجهة، مع إبقاء القيمة الافتراضية 500. ما زال الحد يُطبق لكل مجموعة؛ لذا قد يتراكم حمل كبير عند تشغيل الاستيراد لعدد كبير من المجموعات.

**التحقق:** اختبارات المجموعات والسجل نجحت بعد التغيير. وتُظهر الواجهة حد 10,000، بينما يرفض الخادم أي قيمة أكبر.

## الملاحظات التشغيلية

- **الإجمالي عبر مجموعات متعددة:** حد 10,000 يطبق لكل مجموعة، وليس على إجمالي كل مجموعات الطلب. راقب الحمل إذا بدأ المستخدم مزامنة عدد كبير من المجموعات في آن واحد.
- **الويبهوك يتطلب تهيئة صحيحة في الإنتاج:** يجب تعيين `WHATSAPP_EVOLUTION_WEBHOOK_URL` كعنوان HTTPS عام. عنوان الويبهوك المحلي أو HTTP مرفوض في الإنتاج، وهي حماية مناسبة.
- **الاعتماد على توافق إصدار المزود لم يُختبر حيًا:** الاختبارات تتحقق من أشكال استجابات متوقعة لمسارات مثل حالة الاتصال، المجموعات، الاقتران، والسجل؛ لكنها لا تثبت توافق نسخة Evolution المثبتة فعليًا أو إعداد Baileys/WhatsApp في بيئة الإنتاج.
- **الاعتمادية تعتمد على قاعدة البيانات والتخزين:** أحداث الويبهوك تعالج مباشرة داخل طلب HTTP، وتنزيل الوسائط يعتمد على طابور داخل التطبيق وإعداد التخزين. لم يُختبر اتصال حقيقي بقاعدة البيانات أو Evolution أو مخزن الوسائط خلال هذه المراجعة.

## الضوابط الجيدة الملحوظة

- أخطاء المزود تُحوّل إلى أخطاء typed ورسائل مستخدم موحدة، مع مهلة افتراضية 15 ثانية ومهلة مستقلة لبعض عمليات المجموعات والوسائط.
- سر الويبهوك يُقارن باستخدام `timingSafeEqual` بعد التحقق من تطابق طول البايتات، ويُرفض الحدث عند غياب السر أو عدم تطابقه.
- مسارات واجهة التطبيق تُقيّد بالمساحة الحالية؛ واسم النسخة المقدمة من العميل في فحص الحالة لا يُستخدم قبل مطابقته بالاتصال المخزن للمساحة.
- أسماء النسخ الجديدة مشتقة من مساحة العمل، والحذف يرفض النسخ التي لا يمكن إثبات ملكيتها الفريدة.
- جلب المجموعات لا يطلب بيانات المشاركين، ويُتحقق من أن الاختيارات موجودة في دليل النسخة نفسها.
- تنزيل الوسائط يتحقق من SHA-256 المعلن عند توفره، ويستخدم مسارات تخزين مشتقة/مجزأة، وله محاولات إعادة بحد أقصى وتأخير تصاعدي.
- الرد الآلي يتطلب تفعيلًا واختبارًا للإعدادات، يحدّ طول الرسالة، ويتحقق من الرسائل المباشرة الواردة، ويستخدم سجلًا فريدًا لتجنب معالجة الرد نفسه مرارًا.
- اختبارات الوحدة تغطي مهلات العميل وإلغاء الطلب، تطبيع الحالة، التحقق من سر الويبهوك، الاقتران، ترشيح المجموعات والسجل، وتجميع الوسائط.

## التحقق وحدود المراجعة

- شُغّلت اختبارات Evolution وواتساب ذات الصلة بعد المعالجة: **63 اختبارًا ناجحًا، 0 فشل**، بما فيها اختبارات HTTPS وحد الاستجابة.
- فشل `pnpm --filter @workspace/api-server typecheck` بسبب خطأين في الملفات المحلية غير المتعلقة بالتكامل: `src/lib/meta-order-intake.ts` (تعذر استيراد `menaMetaOrderIntakes` وخطأ استخدام قيمة `null` كفهرس). هذه الملفات كانت ضمن تغييرات غير ملتزمة قبل المراجعة؛ لم تُعدّل ضمن هذا التقرير.
- لم يُفتح ملف `.env` ولم تُقرأ قيم الأسرار. لذلك لم يُتحقق من إعدادات التشغيل الفعلية أو سر الويبهوك أو عنوان Evolution الفعلي.
- لم تُرسل طلبات إلى خدمة Evolution فعلية، ولم يُفحص نشرها أو إصدارها أو سجلاتها أو إعداداتها الداخلية.

## خطة المعالجة المقترحة

1. **تم:** فرض HTTPS لاتصال Evolution في الإنتاج؛ تحقق من أن عنوان الإنتاج الفعلي يستخدم TLS صالحًا.
2. **تم:** وضع حدود حجم لاستجابات Evolution ووسائط واتساب، مع التحقق من الاختبارات المركزة.
3. **تقوية الأسرار:** فصل سر الويبهوك عن مفتاح API واشتراطه في الإنتاج، ثم تدوير المفاتيح عند الحاجة.
4. **تحسين المرونة:** قياس معدل الويبهوك وزمنه وإعادات المحاولة، ومراجعة سقف 1,200 طلب/دقيقة وحد الاستيراد التاريخي وفق استخدام فعلي؛ انقل المعالجة إلى طابور دائم إذا استدعى الحمل ذلك.
5. **قبل الإطلاق النهائي:** اختبار pairing، webhook، مزامنة مجموعة، تنزيل ملف كبير، وإعادة اتصال وفصل على نسخة Evolution المعتمدة في بيئة staging.
